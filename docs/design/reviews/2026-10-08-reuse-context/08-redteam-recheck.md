# B 定向复核原文

## 首次复核

输入为 [05 草稿原文](05-draft-design.txt)与[06 草稿原文](06-draft-implementation.txt)，身份见 A 复核记录。范围：设计 §3、6、7 与实施 §5–6；执行者与最初 B 相同；只读。

定向复核结论：指定风险大多已转成明确合同和验收项；没有发现必须重写 §3、6、7 的设计矛盾。session 映射仍是上线阻断门，文档正确标为 P0，要求实测 host metadata/event；在实测前只能返回 `SESSION_UNBOUND`，不能按 cwd 或模型填入的 ID 猜关联。实现文档 REUSE-07 覆盖双 session、缺字段、恢复/compact 和第四次提醒。

provider 合同已限定三工具、独立打包、不启动全量 SoL、操作者固定 executable/argv、`shell=false`、受控环境/cwd、独立 provider-cache，并要求核对实际 `tools/list` 和发行漂移。超时也区分了可重复缓存与产品效果未知：保留原 attempt，确认进程终态和回执后才可显式新捕获，不能自动重放。实现矩阵 REUSE-01/02/06 覆盖这些路径。**仍需在实现中把发行身份校验落到本机实际包文件及依赖哈希；MCP 自报 metadata 和工具清单都不能证明代码可信或限制进程的 OS 写权限。**应把 provider 定义为受信本地组件的能力边界，不能称为 OS 级隔离。

Hook 约束也已具体化：无 ack 时最多省略三次、第四次提醒；恢复/compact 必发；预算按含 envelope 和 reason 的完整 JSON 做 2048 UTF-8 字节检查；Hook 账本仅存路由元数据、用独立短租约，后台写入门禁不依赖 Hook。REUSE-08 覆盖丢 Hook 后台仍拦截。**剩余一项验证补强：矩阵未明确覆盖两个并发 Hook 争用账本锁、原子写中断，以及证明锁只包账本 I/O、不持锁调用 provider 或执行业务门禁。**建议补入 REUSE-07/08。

上述是文档复核，不是运行时证明；provider 实际包身份、host session 关联、ack 可观测性和锁行为仍须按矩阵实测。

## 最终定向复核

输入为修订后的设计 §3、6、7 和实施 REUSE-07/08，最终文档身份在本轮交付检查固定。

复核通过：§6 按 operation 隔离 cache，并把进程终态、清理、缓存局部效果和 outcome 发布都纳入结算条件。只有效果完整可观察、known-failed outcome 已保存并结算后，才允许显式新捕获；任一环节未知都保持 pending，没有直接换 `request_id` 或“只读可重试”的旁路。

§7 明确投递锁只包账本 I/O，争用或原子发布中断退化为提示与诊断；后台门禁不依赖 Hook。REUSE-07/08 已覆盖并发争用、发布中断及锁内调用检查。§3 也已明确 provider 是受信本地组件，不构成 OS 权限隔离。

仍待宿主与实现验收确认 session 映射、故障切点和锁行为；本轮仅复核文档，没有运行测试。
