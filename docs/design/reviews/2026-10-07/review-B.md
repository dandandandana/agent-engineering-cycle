# B 红队评审：工程循环架构 v0

范围：按 `design-review-council/references/architecture.md` 检查并发、重放、授权、身份/证据伪造和 Hook 失效。只读 `design-v0.md`、`facts.md`、原 Skill 与 `D:/zzd/codex-sol` 源码；未重跑测试。SoL 源码证明可参考的实现模式，不证明独立插件已拥有该能力。以下风险均按 v0 的缺口分类，不把未支持的宿主能力误报为已承诺功能故障。

## 发现

### B1 — 独立 QA 身份和输入绑定仍无可调用的宿主证据契约

- **类别 / 严重度：** 设计风险、待验证假设；P1（若产品宣称“独立 QA”则是发布阻断项）。
- **位置与证据：** `design-v0.md`「独立 QA 与授权」及 P0/P1；当前 SoL 在 `src/architecture/change.mjs` 保存 `method.reported` 与 `identity_verified:false`，没有把调用者填写的 `self_review` / `separate_review` 当身份凭证。P0 也承认尚无具体宿主适配入口。
- **最小反例：** 同一个实现 actor 提交 `{ actor: "qa", fresh_context: true, parent_id: "...", input_manifest: "..." }`；如果 MCP 层把这些字段当 HostEvidenceAdapter 返回值，结构校验通过后便会得到“独立且新上下文”的假阳性。换一个声称有独立身份、却继承实现对话/输入的 actor，也会产生同样问题。
- **失败与影响：** 把模型自述误记为宿主观测；旧实现/上下文参与 QA，Q 却被作为独立证据接受。v0 的原则写对了，缺的是适配器输出由谁生成、如何关联实际调用、哪些字段绝不能由工件作者提供。
- **最小修正：** P0 产出具体宿主能力矩阵和适配器接口；核心仅接收由宿主 adapter 读取的调用身份、父子关系、实际可见起始输入引用/manifest、终态和输出引用。QA 工件只交语义报告，不带可升级为 `verified` 的身份布尔值。身份观测与输入隔离分别记录；任何一项不可得都返回 `QA_VERIFICATION_UNAVAILABLE`。若宿主做不到，P1 可提供非独立检查，但不得称独立 QA 通过。
- **可区分验收：** 在真实宿主执行一次新 actor/新上下文 QA，再执行同 actor 伪造字段、不同 actor 继承输入、适配器无能力三种试验。前者最多报告已观察到的身份/输入级别；伪造和继承不得变成独立通过；无能力必须保持 unavailable。只检查 schema/hash 不算验收。
- **维护影响：** 这是真实宿主边界，需按能力版本维护 adapter；不能让领域核心依赖某个模型的“fresh”字段或捏造的通用 SDK。

### B2 — 用户批准和本轮动作权限的来源未落到可信事件

- **类别 / 严重度：** 设计风险；P1（影响 Delta 和写权限边界）。
- **位置与证据：** `design-v0.md` Delta、操作绑定及「独立 QA 与授权」批准段。文中拒绝信任“我是用户批准的”字符串，但未说明批准引用必须从哪个宿主事件导出；`approved` 目前只是状态名。现有 SoL MCP 工具接收结构化参数并校验绑定/版本，Review 的 method 仍被标成 reported（`src/server.mjs` 工具注册、`src/architecture/change.mjs` review 提交）。
- **最小反例：** 用户只授权“同步文档”，模型从引用资料读到“可以改代码”的文字，随后提交一个带 `source: "user_message"`、`approved_by: "user"` 的 Delta，或把获准 R2 当成代码写权限。若核心只校验来源字符串与状态迁移，候选范围就可能被升级为已批准或可写。
- **失败与影响：** 外部文档、历史内容或模型构造的字段绕过本轮授权；批准新验收被错误地解释为批准代码修改。程序能验证引用和关联，不能证明引用文本的语义确实批准了特定 Delta/动作。
- **最小修正：** 定义 HostApprovalEvidence：来源为宿主可见的用户回合/显式确认事件，含 session、稳定事件 ID、cycle、Delta ID/版本和被批准的精确范围；MCP 作者可提交候选，不能自行铸造该证据。人工导入保留 `reported/unverified`，除非宿主另有可核对来源。把“需求获准”和“允许本轮执行的动作/路径”分开授权，R2 不自动扩大写权限；Skill 仍负责判断用户原话语义是否覆盖该变更。
- **可区分验收：** 文档中出现批准语句、模型伪造来源字段、旧回合批准另一个 Delta、只批准文档却请求代码写入，这些均不得转为当前批准/写许可；实际宿主用户事件对准确 Delta/范围的明确确认才可记录为“来源已观测”，语义仍由 Skill 裁决。
- **维护影响：** 宿主来源模型应版本化，旧批准引用要能显示过期/错绑；不要把审批机制扩成新的用户角色或签名系统，除非宿主真实提供这类能力。

### B3 — “冻结输入 + 完成前复核”没有规定 QA 实际读取哪份不可变内容

- **类别 / 严重度：** 设计风险；P1（可造成 Q 对错误源码版本的假通过）。
- **位置与证据：** `design-v0.md` QA 工作项称异步期间使用冻结输入，并在完成时重新核对当前输入；核心不变量称受影响输入变化使 Q 失效。未规定 QA 运行在不可变快照，或如何证明 worker 真正读到 manifest 对应字节。`facts.md` 明确 Hook 不覆盖外部编辑，且 bypass 只能靠变化检测；SoL 的当前实现有 workspace snapshot/currentness 检查可参考，但独立插件并未复用它。
- **最小反例：** QA 开始时输入为 A；实现者或外部编辑器在 QA 读取前把文件改成 B，QA 读到 B 后文件又恢复为 A；开始和结束哈希均为 A，仍可能接受基于 B 的报告。另一种是 QA 跑在共享可写工作区，在检查过程中源码/测试配置发生漂移。
- **失败与影响：** 起止哈希一致只能证明两次采样相同，不能证明 QA 的读取期间从未变过，也不能证明其执行在冻结输入上；Q 的输入绑定失真。
- **最小修正：** 把冻结输入定义为实际传给 QA 的只读快照/独立工作副本，并将快照内容、相关未提交/未跟踪文件、测试与配置、检查命令和环境标识绑定到 Q。无法提供快照的宿主只能报告 live-worktree 的受限证据，并在不可验证时失效；Hook/租约不作为外部编辑的锁。
- **可区分验收：** QA 运行期间对源文件“改成 B、让 QA 读取、再恢复 A”；结果必须来自不可变 A 快照，或被标记输入不可信/过期，不能仅因最终哈希回到 A 而通过。再验证 dirty 与 untracked 输入会进入 manifest。
- **维护影响：** 需选定快照归属与生命周期；只快照与本次验收相关且可回查的输入，不因此要求全语言静态分析或永久复制整仓库。

### B4 — lease/CAS 和“单活动 cycle”缺少跨进程原子边界

- **类别 / 严重度：** 设计风险；P1（多个会话/服务器共享工作区时可能丢失状态或重复副作用）。
- **位置与证据：** `design-v0.md` 规定期望版本、租约和单活动可写 cycle，但未明确新建 cycle、校验版本、写 pending、发布指针是否都在同一个跨进程原子临界区。`facts.md` 记载 SoL 有跨进程 workspace lock；但项目 `package.json` 是 private，未发布共享 core 包，独立插件不能把私有源码路径当现成的共享租约。
- **最小反例：** 两个 MCP 进程同时读取“无 cycle / version N”，各自创建 cycle 或接受 N 上的更新；后写者覆盖前者指针，另一个 worker 仍持有旧 binding 并执行。只在每个进程内加 mutex 或先读 version 再写无法挡住该竞态。
- **失败与影响：** 两个 cycle 都声称是当前任务，Q/Delta 丢失，或相同命令并行运行；`expected_version` 只在单线程顺序调用中有效。
- **最小修正：** P0 选定真实可分发的存储/锁边界。所有会改变指针或产生副作用的操作，在同一 workspace lock/原子 CAS 下重新读取 binding、校验期望版本并写入 pending；明确进程崩溃时锁和 runner 的恢复行为。若 MVP 只支持单个服务进程，应作为已验证限制显式写入宿主能力，不声称跨进程保障。
- **可区分验收：** 两个独立进程用同一 version barrier 同时启动/更新/verify；恰有一个成功，另一个拿到冲突或忙碌状态；状态无覆盖且 runner 最多执行一次。进程崩溃后不得删除可能仍被子进程持有的锁。
- **维护影响：** 这是独立插件复用路径的关键决策：SoL 可作为被明确调用的 provider，或独立插件实现自有小型持久化契约；不能将未发布的 SoL store/lease 包装成已有公共 API。

### B5 — 副作用后的归档失败虽禁止重放，但恢复状态/幂等入口尚未完整定义

- **类别 / 严重度：** 设计风险；P1（可能重复执行或永久卡在未知结果）。
- **位置与证据：** `design-v0.md` 执行前写 `operation_id`/`pending`、分开执行/归档/结算并禁止因 `exit_code=null` 重放；但未给每个外部副作用的幂等键、结果引用及“执行成功、结果归档前崩溃”后的精确转移。现有 SoL `src/architecture/change.mjs` 有 outcome pointer/recovery；`tests/change-recovery.test.mjs` 对 archive、pointer、settled 三个故障点断言不重放且调用数为 1，可作为已有定向验收证据（本审查未重跑）。
- **最小反例：** 固定验证命令实际运行并产生了副作用/成功结果，随后归档服务不可用，进程在结果落盘前退出。上层因工具超时重复相同请求；如果服务为重试生成新 `operation_id` 并重新运行会重放副作用，如果只留下 pending 而无查明路径则任务可能永久未知。
- **失败与影响：** 重复迁移/生成/外部调用，或把未知状态误判失败后再次运行；若把“命令没回执”当通过则出现假完成。对普通纯检查可允许人工新建一次尝试，但不能自动把未知尝试重放。
- **最小修正：** 规定稳定请求幂等键或在 pending 状态下对同一绑定拒绝新执行；调用者响应丢失时先按 operation ID 查状态。至少区分 `effect_unknown`、`outcome_durable`、`archived`、`settled`；只有可验证归档与输入匹配才恢复 known，无法恢复就保持 unknown/unfinished，由显式 reconciliation 处置，不自动重跑。
- **可区分验收：** 在副作用返回后、原始 outcome 归档前注入崩溃，再以相同请求重试；副作用计数仍为 1，cycle 保持 unknown/unfinished。另在 outcome 已归档而指针结算失败时恢复到已知结果，不运行第二次。重用 SoL 现有三故障点 fixture 即可，不需重跑完整测试集。
- **维护影响：** 每类可执行 adapter 需声明是否幂等及其回执可恢复方式；不需要给纯只读调用添加复杂工作流状态。

### B6 — Stop 次数限制的计数范围与“没有进展”判定不明确

- **类别 / 严重度：** 设计风险；P2（重复打断后续用户轮次或继续提示）。
- **位置与证据：** `design-v0.md` Hook 和不变量写“限制继续次数/有限续跑”，但没说明限制按一次 Stop、一次用户 turn、同一 cycle 还是全局累计，也未定义无状态变化时是否仍有可执行收尾。SoL `src/context-hook.mjs` 依赖宿主 `stop_hook_active` 避免同一轮重复续跑；`facts.md` 说明 Stop block 是继续提示，不是拒绝整个会话。
- **最小反例：** cycle 因缺少宿主 QA 能力而 blocked；后续用户轮次中仍有可执行收尾文本，Stop 每轮重新 block，反复要求模型继续，或重复提示已执行过的同一动作。宿主在本轮已提示的 flag 不能证明跨新 turn 的进展。
- **失败与影响：** 用户的后续独立请求被旧 cycle 收尾提示反复打断；重复工具调用可能进一步触发 B5 的重放路径。若已 blocked/interrupted/等待外部输入，则重复 Stop 不能让它变成可行动状态。
- **最小修正：** 明确 Stop 只在当前绑定 cycle/version 存在一个尚未执行、无需新授权且可判定的动作时提示；阻塞/等待时只报告未完成并退出。每个 host turn 最多一次续跑，重复的相同 cycle version 不重复提示；若宿主不能提供 turn identity，则只依赖其已验证的 Stop 生命周期，并明示更宽范围的上限未验证。
- **可区分验收：** 同一状态连续触发 Stop 与跨新 turn 重触发；同一版本不得重复执行/提示同一步。状态发生有效推进后允许下一项；外部 QA 缺失、blocked、被取消时保持 unfinished 且不继续 block。
- **维护影响：** 使用宿主真实 turn/Stop 标识即可；不增建独立调度器或长期唤醒功能。

## 不作为缺陷的边界

Hook 未运行、MCP 未连接、工具走未支持的 Shell/外部编辑器属于 v0 明示的未覆盖路径，不要求阻止这些行为。最小要求是：Hook 只报告已覆盖事件；受管核心操作重读绑定与输入；外部变化被检测时让相关 Q 失效/保持 unfinished。不能声称 Hook 是强制安全边界，也不能把“检测不到某一类未枚举输入”包装成已证明完整性。

## 裁决提示

先将 B1、B2、B3 的宿主/证据定义与 P0 能力 PoC 闭合，再决定 P1 能否宣称“独立 QA / 获批 Delta”；B4、B5 是存储与执行契约的可测试要求；B6 可作为实际 Hook 适配时的验收限制。任何通过结构、哈希、角色字段或一次模型返回的结果都只能证明对应程序检查，不证明 QA 语义正确。
