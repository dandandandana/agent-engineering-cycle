# D 可维护性审查

范围：独立插件落点、SoL 复用/分发边界、状态事实来源、旧 Skill 项目接入与变更范围。只读检查了 `design-v0.md`、`facts.md`、`agent-engineering-cycle` Skill 契约，以及 codex-sol 当前包/插件/MCP 接口与相关源码。复用事实包中的同一源码检查证据：44 pass、1 个 Windows chmod skip；没有重跑测试。以下是静态设计审查，不证明宿主实际能跨插件调用、Hook 覆盖或 QA 身份观测。

## D1 — 独立插件 P1 尚无可交付的受管写入/验证提供方

**类别与程度：设计风险；在 P1 前属于阻塞项。**

**位置与证据：** `design-v0.md`“与 codex-sol 的关系”第 24 行、“拟定公共操作”第 43–53 行及 P0/P1 第 81–83 行将共享 MCP 或共享包留给 P0 选择，但 P1 已要求受管 write/verify。当前 `D:/zzd/codex-sol/package.json:2-18` 将包标为 `private: true`，没有 `exports` 入口或发布契约；`src/runtime.mjs:11-28` 的 `createSolRuntime` / `configureRuntimeChanges` 是源码级导出，不构成稳定可分发的共享包 API。可见工具界面在 `src/server.mjs:65-68,83-88,101-115`。其中 SoL 的 `sol_change_open` 需要最新架构查询和模块 UID；`src/architecture/change.mjs:25-30` 的 scope 也强制 `module_uid`。插件清单只声明自身 launcher/server（`.codex-plugin/plugin.json`、`mcp.json`），没有 SoL 依赖版本或能力契约。

**触发 → 失败 → 影响：** 在没有 SoL 的独立安装中，直接导入 `../codex-sol/src` 既跨仓库私有耦合又无法按包版本分发；依靠已安装 SoL 时，未登记架构的 Python/文档项目无法使用 `sol_change_open` 的受管变更路径。若为这些项目另写一套通用状态、租约、写入和校验协调器，便会复制 SoL 的核心不变量；若退回未绑定的宿主写入，则 P1 不能声称设计中写入前同租约复核的保证。P0 已有“可行/不可行分支”的方向，但尚未定义不可行时 P1 的落点与承诺边界。

**最小改进：** 将 P0 作为明确的 go/no-go 门：先用真实安装方式分别验证 standalone、SoL 已安装，以及无架构登记 Python 三种能力组合；确定一个版本化的 `Write/Verify/Evidence` provider 契约（安装/连接发现、可用能力、错误、输入/输出身份、单一写入 owner）。只有现存 MCP 工具确实满足契约时，才做可选适配；不能把私有源文件导入、逐项翻译整套 ChangeCoordinator，或把 SoL 可选安装偷偷变成独立插件前提。若宿主能力不能提供声明的受管门禁，要在 P1 范围和 UI/工具结果中标明实际保证级别，不宣称受管写入已实现。

**验收：** 在干净安装目录完成独立插件发现/启动；分别在 SoL 未安装和已连接、无架构登记的 Python 项目运行最小写入与固定检查。记录每种组合的真实工具/能力、授权绑定、检查回执及失败方式；验证缺 provider 时不会静默进入“受管成功”路径。不得以源码可读或文档声明代替安装试验。

**维护影响：** 先锁定 provider 契约可避免每个宿主都复制文件系统安全、租约和恢复语义，也能让 SoL 保持独立版本节奏。若某项通用能力目前只存在于 SoL 私有源码，应由后续明确授权的 SoL 变更建立/发布稳定接口；本轮独立插件设计不应把它当已有依赖。

## D2 — 工件模型可能把 Skill 的语义记录再建成第二事实源，并预埋过宽操作面

**类别与程度：设计风险；进入 P1 前应收紧归属。**

**位置与证据：** `design-v0.md:32-41` 同时提出外部权威、完整 R/D 工件、I 工件、Q 证据、Delta 状态和当前 Cycle 指针；`design-v0.md:47-53` 又提出职责工件 prepare/submit、QA start/status/result、Delta reconciliation、完成等多类操作。已安装 Skill 明确说明它是协调指令而非状态执行器，并“不创建第二套 PRD/任务系统”（`agent-engineering-cycle/SKILL.md:9-21`）；状态契约要求沿用原格式，一个状态只在真实 owner 位置维护，不复制整份需求/设计（`references/state-contract.md:7-15`）。

**触发 → 失败 → 影响：** 用户在原 `docs/design/requirements.md` 修订验收，或实现者更新项目自己的 I 文档后，如果插件还保存可编辑的 R/D/I/Delta 正文和独立状态，就必须决定以哪份为准、同步哪些版本及 Hook/MCP 如何暴露冲突。若把旧文档拷成插件工件，随后只改一边会造成双主控；若将每类工件变为强制结构化提交，普通 Python/纯文档仓库就要迁移 Skill 从未要求的 schema/角色流程。与此同时，每个重复字段都要跨 MCP schema、Hook 投影、Skill 指令、恢复逻辑和测试保持兼容。

**最小改进：** 在设计中为状态所有权补一张短表即可，不增加通用注册框架：原项目文档拥有 R/D/决定/Delta 正文及 I 说明；项目配置拥有检查命令与 QA 策略；验证执行端拥有原始运行回执；cycle 核心只拥有活动 cycle/version、授权 scope、pending operation/已观察副作用、阻塞和同步阶段，以及到上述来源/回执的引用与必要摘要/内容身份。源文快照若为取证需要，应是不可编辑的历史证据，不能用来改写权威正文。P1 先实现真正参与硬门禁的最小状态操作；在具体消费者证明需求前，不建立通用 role/output-schema 工件总线或每类工作项的全套生命周期工具。

**验收：** 使用现有 `docs/design`、自由格式实现状态和未结构化 QA 记录的项目启动 cycle；确认插件能显示原来源、把未知字段标成未知，并在需求改动后更新来源身份/使受影响 Q 失效，而不会强制重写原件或生成第二份可编辑要求。随后只改项目 I 记录，确认其余状态无需同步复制。检查 MCP 响应、Hook 摘要和恢复读取对同一字段只有一个 owner。

**维护影响：** 按 owner 区分语义事实、程序事实和操作状态，会把项目本已负责的内容留在原位置，减少字段迁移、兼容垫片和重复更新；窄操作面也限制插件变成第二个工作流框架。

## D3 — QA 策略自身的身份与受影响证据范围尚未落到可判定条件

**类别与程度：待验证假设/设计风险；影响旧 Q 的复用正确性。**

**位置与证据：** `design-v0.md:35,41,50` 说明 Q 与受验输入/检查配置绑定、输入变化使受影响 Q 失效，但没有明确“有效 QA 策略”由哪个来源拥有，或内置策略变化如何进入版本身份。Skill 要求 Q 绑定需求、相关源码/测试/配置和环境，并只复验受影响边界（`agent-engineering-cycle/SKILL.md:61`；`references/state-contract.md:29-40`）。SoL 当前实现已有可参考的具名边界：`src/architecture/change.mjs:16,303-305,605-608` 将 review policy、规则配置摘要纳入当前性检查/basis。

**触发 → 失败 → 影响：** QA 命令、必需检查集合或插件内置判定策略变化，而该策略不在输入 manifest 内时，旧 Q 可能仍被标为 current，并错误支撑完成；如果任何细小配置改动都让整轮 Q 全部失效，又会重复运行未变的检查并使维护成本上升。设计目前无法明确区分这两种结果。

**最小改进：** 对每条完成门禁记录生效的策略来源身份：项目文件/命令的相关摘要，或插件策略 ID+revision；与要求版本、输入产物、环境身份分列。变更时保留旧 Q 为历史，按“被影响的必需检查”重新评估 currentness；只有可证明相同输入/规则的回执才允许复用。若策略无法取得稳定身份，应返回 `stale/未证实`，不可默认通过。

**验收：** 固定同一源码，只改一次 QA 配置/策略：旧证据仍可查看但不能满足新策略；受影响检查重跑，未受影响检查只有在其配置/输入身份匹配时才能复用。再确认恢复后结果与首次运行一致，不需要哈希全仓库。

**维护影响：** 明确策略版本owner与失效粒度，避免每加一条检查就更新多个隐式字段，也避免全量失效掩盖检查规则已经变化。

## D4 — 首次接入旧 Skill 状态与中断写回的迁移/恢复协议缺少可执行边界

**类别与程度：设计风险；旧项目兼容与 Delta 原子性依赖此处。**

**位置与证据：** `design-v0.md:37,41,52-53,73,77` 提到同步状态、pending operation、批准引用、恢复核对与完成前置条件，但没有规定首次 adoption 如何处理既存自由格式状态，也没有定义写回前后如何判断某个 Delta 已落到原 owner。Skill 状态契约允许自由格式/单文档状态、已有主控优先，不自动迁移或重编 ID（`state-contract.md:7-15`），并要求多文件写回逐项核对、恢复时不重放已完成副作用（`state-contract.md:53-55`）。

**触发 → 失败 → 影响：** 项目已经按旧 Skill 有 R/D/I/Q/Delta 记录但无插件 schema；若插件假定标准字段完整，就会要求用户迁移整套文档或把解析猜测标成可信状态。另在 Delta 写回原需求文件后、插件完成同步记录前中断，若只看到 `pending` 而没有目标来源的前/后身份，恢复只能重复写入或猜测 `incorporated`，会丢失旧要求、制造重复条目或宣布未完成记录已完成。

**最小改进：** 保留 Skill 原流程与文件格式；首次启用只登记用户确认的主控路径/锚点和可核验内容身份，未映射部分标 `unknown/unmapped`，由 Skill/主 Agent照原契约恢复，不自动改写旧文档或生成新的权威副本。Delta 写回最少记录目标 owner、写入前身份、预期写入后身份和 operation ID；恢复时先读目标：匹配后态则结算已同步，匹配前态才允许安全续写，第三种状态标冲突并保留记录。无需为此引入通用事务引擎。

**验收：** 用一份已有 `docs/design` + 自由格式 `IMPLEMENTATION_STATE.md` 的项目首次启用；应保留原文与 ID，可恢复缺失/陈旧信息但不自动迁移。再在 Delta 多文件写回的各个中断点恢复：结果分别应为已同步、可安全续写或冲突待处理，不出现重复增量、不覆盖外部修改，也不把未同步当作 completed。

**维护影响：** 明确 adoption 是引用和核对而非全仓库迁移，让新插件可与已安装 Skill 并行演进；窄化恢复判定避免额外维护分布式事务抽象。

## 可复用证据与边界

建议父 Agent按上述四个变化场景修改设计/验收，而不是扩展成源码共享库、全语言架构登记或跨仓库私有导入。复用 facts 中的 44 pass / 1 skip 仅说明当前 SoL 源码在当时同一输入下的本地检查结果，不证明其 MCP 可被独立插件依赖、Python 项目适配、策略身份自动变化检测或宿主运行表现；这些必须由 P0/后续宿主验收提供。
