# 工程状态与恢复契约

用于准备写入、接手陈旧状态或同步多份工程记录时。字段是最低语义要求，沿用项目现有格式，不将下方示例当成新 Schema 或每轮必建文件。

## 载体与权威

先定位已有启动入口和权威需求、设计、决定、QA 记录。已有 ID 优先；没有 ID 时可以用 `文件路径#章节/局部别名` 回链原文，不全库重编号。I、Q 和 Delta 引用原来源，不能另建一份能够独立决定范围的摘要。

在现有入口/恢复点写清实际主控、需求/验收来源、设计/蓝图来源、下一执行指针、Q 位置及各写入 owner；可以只是一行链接，不新建登记系统。`.prd/` 与蓝图并存时沿原声明和引用链确定归属，既有主控继续拥有计划/NEXT。

一项状态只在一个实际 owner 的原位置维护。多个目录并存时依据已有确认和引用关系选择，不按 `.prd/` 等名字自动迁移；主控不明确且会影响授权时保留原件、继续独立调查。

缺实现记录时，在原文档目录增加最小实现状态载体，并从已有执行入口链接。小任务可将 I、QA、Delta 放一个文档中；长期独立维护内容再拆。没有文档的小型工程可使用 `docs/IMPLEMENTATION_STATE.md`；完整新项目契约交原需求工作流，不为此强建五层目录。

只写当前变化、恢复必需的不变量和到原文的链接。旧决定、验收与证据保留可回查的历史；不用每轮重写整份需求/设计或复制所有源码。过长的历史可按项目已有方式归档，当前摘要链接历史，不能静默丢掉未决项。

## 实现记录必须能回答

- **目标与边界**：本轮用户目标/场景、R/D 来源与修订、REQ/验收 ID、授权依据、非目标和保持行为。
- **实际系统**：入口、关键模块责任/调用方/数据流、状态或配置的单一来源、公共接口兼容情况。静态声明与已观察运行分开。
- **决策与偏差**：使用/拒绝方案的简短公开理由及来源；刻意保持的结构、不变量；设计与实现不同之处及影响。不需要保存隐含推理过程。
- **实现覆盖**：各相关需求的已实现/部分实现/未实现，指向文件/符号；不把设计稿、占位或测试声明当实现。
- **关键机制**：只在有帮助时为重要函数/组件补充职责、数据流、依赖和维护不变量的实现说明；按 [implementation-notes.md](implementation-notes.md) 引用源码及原说明，不复制成第二份 I 正文。
- **已知限制**：缺陷、workaround、临时实现、未测路径、阻塞条件与 owner；不能只写“以后优化”。
- **验证**：指向 Q 的原始命令/观察、输入状态、环境、结果与限制。旧版本通过只作为历史证据。
- **恢复点**：当前阶段、最后已完成动作、未完成/在运行的任务及 ID/owner、下一安全动作、待用户决定与同步状态。

实现状态和验证状态分列。例如“源码已实现，真实浏览器验收 blocked”，不能合并成“完成”。没有对应检查时写未配置或未运行及影响，不虚构命令。

函数/组件说明是 I 的可选索引，不替代原需求、设计、代码注释或 QA。运行时目标与引用的精确字段、全文件身份、当前性状态和授权边界见[实现说明契约](implementation-notes.md)；没有声明实现目标的既有 cycle 不要求新增登记。

## 证据与版本绑定

每份 Q / 一组相同输入的检查记录至少包含：

1. REQ/验收 ID 和修订身份，能回查当时的要求；不能只链接一直变化的正文。
2. 实际受验收的相关源码、测试、配置、生成产物的范围清单与可比较的内容/版本标识。
3. 关键运行时/工具版本、平台、必要前置条件、命令与工作目录；只记录安全配置名或脱敏摘要。
4. 运行/观察结果、退出状态、证据位置、没有覆盖的边界和执行者。

使用项目已有快照/工件版本即可。Git 项目至少识别 HEAD 以外的暂存、工作树和相关未跟踪修改；没有可信快照时可用标准工具记录窄范围文件 SHA-256。仅文件名、时间戳或 HEAD 不足以证明内容一致。只对实际相关输入建立清单，不每轮哈希全仓库或创建专用指纹框架。

复用前核对清单与关键环境。改变或无法确认的项标 `stale/未证实`，重新验证受影响边界；未改变且有足够绑定证据的结果保留。报告可以有一组绑定身份、多项 REQ 结果，不复制大量相同元数据。

## Delta 合入与同步

每项变更保留来源、旧/新行为、被影响/替代 ID、原因、授权依据及状态。可用项目现有状态词，明确区分：

- `proposed`：建议，不能改变权威需求或启动实施。
- `approved`：用户或已有授权已覆盖此项；尚未写回权威位置时标“待同步”。
- `incorporated`：已由原 owner 合入原需求/决定来源，并保留旧版本与替代关系。
- `rejected/deferred`：有处置依据，原要求仍有效。

`incorporated` 仅表示需求记录已合入，实施和验证另记。获准的需求变更可以形成 R2，而代码仍停在 R1；I 应明确“符合旧行为，新要求未实现/未验证”，不能假称代码已同步。

权限不允许写回主控时，输出待同步建议；保留 approved-but-unreconciled，不在 I 或新文件里悄悄建立第二套权威。没有用户变更批准时，不能把失败的 R1 改成 R2 让结果通过。

多文件写回先记录本次相关版本和待同步项，逐项更新原 owner 位置，全部核对后才关闭同步状态。中断恢复时比较主控、I/Q/Delta 与源码；原记录不一致就保持未同步，不能把“文档曾开始写入”视作事务已完成。

## 最小记录示例

下面是虚构项目的格式示例，不是待执行结果：

```markdown
# 实现状态 · cycle-3
目标来源：docs/design/requirements.md@R3，REQ-7；保留 API 与原错误类型。
代码身份：项目快照 artifact-31（含未提交修改）；输入清单见 QA-12。
阶段：实现已交付，QA 受限；记录同步完成。

| 需求 | 实现/位置 | 验证 | 已知限制 |
| --- | --- | --- | --- |
| REQ-7 | 已实现，src/policy.py::admit | 本地边界检查 pass，QA-12 | 外部集成 blocked |

实际路径：controller → policy；配置 owner 为现有 config 模块。
决定：保持同步 API；原因与范围见原 DEC-2。没有设计偏差。
问题：外部服务不可达；不以 mock 替代真实集成。
下一安全动作：设施恢复后执行 QA-12 所列集成；没有新功能授权。
在运行任务：无。待决定：候选 CR-4，不属于本轮。
```

写给下一位 Agent 的是当前可信事实与安全动作，不能只有时间线、文件列表或“全部通过”的总结。
